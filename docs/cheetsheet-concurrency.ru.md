# Конкурентность и параллелизм

## Определения

**Конкурентность (concurrency)** — это способ организовать программу как независимые вычислительные части, которые могут продвигаться вперёд не по строгому порядку или в частичном порядке, не меняя ожидаемый результат. Эти части могут чередоваться при разделении времени процессора или выполняться параллельно.

**Параллелизм (parallelism)** — это одновременное выполнение нескольких частей работы.

Кратко: **конкурентность — о проектировании программы; параллелизм — о её выполнении.** Это различие есть уже в ранних работах, например в *Solution of a Problem in Concurrent Programming Control* Эдсгера Дейкстры (1965): конкурентное программирование и параллельное выполнение связаны, но не тождественны.

Аналогия с кофейней:

- Конкурентность: разделить процесс на приём заказов, помол кофе и приготовление напитка, чтобы этапы могли координироваться.
- Параллелизм: добавить ещё одного бариста и кофемашину, чтобы обслуживать двух клиентов одновременно.

Одни и те же принципы конкурентности применимы к программе на одноядерной машине, многоядерной машине или нескольким машинам в распределённой системе.

## Конкурентность как модель программирования

Модели программирования по-разному разделяют задачу:

- Объектно-ориентированное программирование делит задачу на взаимодействующие структурные компоненты.
- Функциональное программирование делит задачу на функциональные компоненты, вызывающие друг друга.
- Конкурентное программирование делит задачу на временные компоненты, которые обмениваются сообщениями и могут чередоваться или выполняться параллельно.

Communicating Sequential Processes (CSP) — математическая модель, повлиявшая на Go. Система состоит из независимых последовательных процессов, которые общаются передачей сообщений. Общение может быть синхронным: отправитель не может продолжить работу, пока получатель не примет сообщение. Так ведёт себя небуферизированный канал Go.

## Сложность и deadlock

Состояние последовательной программы приблизительно состоит из значений в памяти и текущей точки выполнения. В конкурентной программе общее состояние — это комбинация состояний всех компонентов.

Независимые компоненты могут выполняться во множестве разных порядков, поэтому количество возможных общих состояний быстро растёт. Из-за этого сложно полностью проанализировать состояние программы; возникают возможности для deadlock, data race и ошибок порядка выполнения.

## Производительность

Конкурентный код не становится автоматически быстрее последовательного. Фактическая производительность зависит от того, может ли работа выполняться параллельно, от доступных CPU, блокирующих операций, `GOMAXPROCS` и накладных расходов на goroutine, планирование, синхронизацию, каналы, mutex и contention.

Goroutine дешевле OS thread, но не бесплатна. Создание, планирование, переключение, синхронизация и обмен данными между goroutine имеют стоимость.

Подходящие случаи для конкурентности:

- независимые CPU-интенсивные части работы;
- независимые I/O-операции;
- pipeline;
- worker pool;
- обработка запросов.

Неподходящие случаи:

- мелкие задачи, в которых координация дороже самой работы;
- строго последовательная логика;
- задачи с большим объёмом общего изменяемого состояния;
- задачи, требующие слишком большой синхронизации.

## Планировщик Go

Планировщик Go обычно описывают моделью G-M-P:

```text
G — goroutine
M — OS thread (machine)
P — логический процессор, необходимый для выполнения Go-кода
```

Go использует планировщик M:N: множество goroutine мультиплексируется на меньшем или равном количестве OS thread. `P` содержит ресурсы планировщика и очередь готовых goroutine. Runtime использует локальные очереди, глобальную очередь и кражу работы (work stealing), чтобы распределять готовые goroutine.

`GOMAXPROCS` ограничивает количество `P` и, следовательно, количество OS thread, которые могут одновременно выполнять пользовательский Go-код. Обычно значение равно числу доступных CPU. Он **не** ограничивает общее число OS thread: runtime может создавать дополнительные thread, когда некоторые из них заблокированы в системных вызовах.

Обычно goroutine находится в одном из следующих состояний:

```text
running   — выполняется сейчас
runnable  — готова к выполнению и ожидает процессорное время
waiting   — заблокирована на I/O, канале, mutex, syscall или другом событии
```

Выполняющаяся goroutine может быть вытеснена (preempted) и возвращена в состояние runnable. Ожидающая goroutine становится runnable, когда завершается событие, которого она ждёт.

Начиная с Go 1.14, планировщик поддерживает асинхронное вытеснение (asynchronous preemption), поэтому длинно работающие goroutine можно прервать, чтобы другие goroutine получили процессорное время. Ранние версии сильнее опирались на кооперативные безопасные точки и блокирующие операции.

# Goroutine

## Process, thread и goroutine

**Process** — экземпляр программы с управляемыми операционной системой ресурсами: памятью, процессорным временем, файловыми дескрипторами и как минимум одним thread. Отдельные process взаимодействуют через определённые механизмы межпроцессного взаимодействия.

**Thread** — управляемый ОС контекст выполнения. Его stack хранит вложенные вызовы функций, локальные значения и состояние выполнения. Планировщик ОС выделяет thread процессорное время и может вытеснить один thread, чтобы запустить другой.

**Goroutine** — лёгкая единица конкурентного выполнения, которой управляет Go runtime. Ключевое слово `go` запускает функцию в новой goroutine:

```go
go work()
```

Функция может принимать аргументы, но не может напрямую вернуть значение вызывающей стороне. Результаты нужно передавать через канал, общее состояние, callback или другой механизм координации.

## Goroutine и OS thread

- Goroutine планируются Go runtime; thread — операционной системой.
- Goroutine начинают работу с небольшим stack, который растёт и уменьшается по необходимости; stack OS thread обычно значительно больше.
- Создание и переключение goroutine требуют меньше ресурсов, но они всё равно потребляют память и время планировщика.
- OS thread могут иметь приоритеты; goroutine не имеют назначаемых пользователем приоритетов.
- Множество goroutine может выполняться на меньшем наборе OS thread.

При каждом вызове функции проверяется, достаточно ли места в stack goroutine. Runtime увеличивает stack при необходимости. Точный начальный размер и стратегия роста — детали реализации, которые могут меняться между версиями Go.

## Жизненный цикл

Goroutine запускается при выполнении оператора `go` и завершается, когда её функция возвращает управление. Если завершается `main` goroutine, завершается вся программа, даже если другие goroutine ещё не закончили работу.

Создание goroutine всегда ставит вопрос о жизненном цикле: как она завершится? Обычно у goroutine должно быть понятное условие завершения, закрытие входного канала или сигнал отмены.

Помимо `main` goroutine Go runtime запускает внутренние goroutine для задач вроде garbage collection и управления runtime.

## Как runtime планирует goroutine

Runtime отслеживает goroutine, OS thread и логические процессоры. Готовая к запуску goroutine выбирается и назначается OS thread, связанному с `P`. Она выполняется, пока не завершится, не заблокируется, не уступит выполнение или не будет вытеснена.

Поведение при блокировке зависит от операции:

- Блокировки на каналах и mutex известны Go runtime, поэтому он может приостановить только goroutine и запустить другую.
- Блокирующий системный вызов может заблокировать OS thread. Runtime может отсоединить его `P` и использовать или создать другой thread, чтобы продолжать выполнение Go-кода.
- Поэтому общее число OS thread может быть больше `GOMAXPROCS`, хотя пользовательский Go-код одновременно выполняют не более `GOMAXPROCS` thread.
- Сетевой I/O обычно использует netpoller runtime. Пока netpoller ждёт готовности, goroutine приостановлена, поэтому OS thread обычно остаётся доступным.
- Файловый I/O в целом ближе к блокирующему системному вызову и может блокировать OS thread.

Большинство I/O API Go всё ещё выглядят синхронными с точки зрения goroutine: чтение файла или сети, HTTP-вызов или запрос к базе данных возвращают управление только после завершения. Конкурентный I/O обычно выражают запуском таких вызовов в goroutine и координацией с помощью channels, `WaitGroup`, `errgroup` или отмены через context.

## Stack, heap, closure и race

- **Scope** — область исходного кода, где идентификатор видим. Она не определяет, будет ли значение размещено в stack или heap.
- **Stack** хранит кадры вызовов, локальные значения и состояние выполнения. У каждой goroutine свой stack.
- **Heap** хранит значения, которые нельзя безопасно оставить в кадре stack или которые должны пережить его. Выделениями в heap управляет garbage collector.
- **Escape analysis** — анализ компилятора, который решает, может ли значение остаться в stack или должно перейти в heap.
- **Closure** захватывает переменные из окружающей лексической области видимости. Closure в сочетании с goroutine и общими изменяемыми переменными — частая причина ошибок.
- **Data race** — конкурентный доступ к одной области памяти, при котором хотя бы один доступ является записью, а доступы не синхронизированы должным образом.

## Leaks и координация

**Goroutine leak** возникает, когда goroutine никогда не завершается — обычно потому, что навсегда заблокирована на канале, I/O-операции, lock или из-за отсутствующего сигнала отмены. Утёкшие goroutine удерживают память и другие ресурсы и могут постепенно ухудшать работу программы.

`sync.WaitGroup` ожидает завершения группы goroutine. Он координирует завершение, но не отменяет goroutine и не обрабатывает их ошибки.

`context.Context` передаёт отмену, deadline, timeout и значения уровня запроса между границами API. Его обычно используют, чтобы goroutine могли остановиться, когда их работа больше не нужна.

Goroutine обмениваются данными через channels или через общее состояние, защищённое примитивами синхронизации, например mutex. “Share memory by communicating” — полезный принцип Go, но синхронизированное общее состояние также распространено и иногда проще.

# Channels

## Назначение и блокирующее поведение

Channels управляются Go runtime, а не операционной системой. У них две роли:

- канал передачи типизированных данных;
- механизм синхронизации между goroutine.

Канал сохраняет порядок значений, отправленных одним отправителем. Отправка блокируется, пока канал не сможет принять значение, а получение блокируется, пока значение не станет доступным.

## Небуферизированные channels

Небуферизированный channel не имеет ёмкости для хранения. Отправка блокируется, пока другая goroutine не получит значение, а получение блокируется, пока другая goroutine не отправит значение.

Это делает небуферизированный channel точкой синхронизации и атомарной передачей значения между отправителем и получателем: обе стороны должны участвовать, прежде чем какая-либо операция завершится.

## Буферизированные channels

Буферизированный channel имеет фиксированную ёмкость:

- отправка блокируется, когда буфер заполнен;
- получение блокируется, когда буфер пуст;
- в остальных случаях операция может выполняться без ожидания другой стороны в тот же момент.

Буфер изменяет блокирующее поведение, но не отменяет необходимость рассуждать о синхронизации, ownership и backpressure.

## Nil channels и garbage collection

Нулевое значение channel — `nil`. Отправка в nil channel и получение из него блокируются навсегда. В `select` ветка с nil channel отключена, что может быть полезно для динамического включения и выключения веток.

Channels не требуется закрывать для garbage collection. Если ни одна достижимая goroutine или переменная не ссылается на channel, он может быть собран, даже если его буфер содержит значения. Закрытие имеет семантический смысл — оно сообщает, что новых значений не будет, — а не служит очисткой ресурсов.

## Закрытие channel

Закрытие channel сообщает, что новых значений больше не будет.

- Получатели сначала извлекают все буферизированные значения.
- Последующие получения немедленно возвращают нулевое значение типа элемента и `ok == false`.
- Отправка в закрытый channel вызывает panic.
- Закрытие уже закрытого channel вызывает panic.

Используйте форму с `ok`, если получателю нужно отличить настоящее нулевое значение от закрытого channel:

```go
value, ok := <-ch
```

Обычная отправка не является broadcast: одно значение получит один получатель. Закрытие работает как уведомление для всех текущих и будущих получателей, поскольку получение больше не блокируется. `context.Context` использует этот подход, закрывая `Done()` при отмене.

## Ownership

Ownership channel означает, что нужно определить, кто создаёт канал, кто отправляет и получает значения, а также кто его закрывает. Обычно закрытием владеет отправляющая сторона, потому что только отправители знают, когда новых значений больше не будет.

У channel может быть несколько отправителей или получателей. Каждое отправленное значение получает только один получатель, поэтому общий входной канал удобно использовать для распределения работы между worker goroutine. Если отправителей несколько, они должны координировать закрытие, чтобы никто не отправил значение после закрытия channel.

Направленные типы channel явно показывают намерение в API:

```go
var receiveOnly <-chan int // только получение
var sendOnly chan<- int    // только отправка
```

Ссылка только для получения не даёт права отправлять или закрывать channel. Ссылка только для отправки не позволяет получать значения; она может закрыть channel, поскольку закрытие относится к отправляющей стороне.

## Select

`select` ожидает набор операций отправки и получения через channels и выполняет одну операцию, которая может продолжиться.

- Если готова одна ветка, выполняется она.
- Если готовы несколько веток, одна выбирается псевдослучайно.
- Если ни одна ветка не готова, но есть `default`, выполняется `default`.
- Если ни одна ветка не готова и `default` отсутствует, `select` блокируется.

### Multiplexing

`select` позволяет одной goroutine ждать несколько операций с channels и реагировать на ту, которая станет готова первой. Его часто используют для объединения событий, ожидания результата или отмены, а также координации этапов pipeline.

### Timeout

Timeout можно реализовать, выбрав в `select` между операцией и `time.After`, либо используя context с deadline. Это предотвращает бесконечное ожидание операции с channel.

### Cancellation

Отмену обычно обрабатывают через выбор `ctx.Done()` в `select`. Когда context отменён, его канал `Done` закрывается, и все goroutine, ожидающие его, могут остановиться.

### Риски `default`

Ветка `default` делает `select` неблокирующим. Это полезно, когда пропуск недоступной операции намеренный, но неосторожное использование может привести к busy loop, высокой загрузке CPU, потере backpressure или незаметному пропуску работы.

## Частые ошибки и deadlock

Deadlock возникает, когда goroutine навсегда заблокированы и ни одна из них не может продвинуться. Частые ошибки, связанные с channels:

- отправка в закрытый channel;
- закрытие channel со стороны получателя;
- закрытие channel, пока другие отправители ещё могут им пользоваться;
- отправка в небуферизированный channel без получателя;
- получение из channel без отправителя;
- `range` по channel, который никто не закроет;
- утечка goroutine, заблокированных на channels;
- ожидание `WaitGroup`, чей счётчик никогда не дойдёт до нуля;
- использование `time.Sleep` вместо правильной синхронизации.

# Worker Pool

## Паттерн

Worker Pool v1 использует фиксированное число goroutine для обработки потока задач:

```text
producer -> jobs channel -> N workers -> results channel -> consumer
```

Вместо создания отдельной goroutine для каждой задачи pool запускает `workerCount` goroutine. Каждый worker последовательно получает задачу, вызывает handler, отправляет результат и завершается, когда `jobs` закрыт и обработан.

Это **ограниченная конкурентность (bounded concurrency)**: одновременно выполняется не более `workerCount` handler.

## API

```go
type Job struct {
	ID      int
	Payload string
}

type Result struct {
	JobID int
	Value string
	Err   error
}

func Run(workerCount int, jobs <-chan Job, handle func(Job) Result) <-chan Result
```

Направленные типы показывают намерение: pool только получает данные из `jobs`, а вызывающий код только получает данные из возвращённого канала результатов. Текущая реализация приводит неположительное `workerCount` к одному worker.

## Жизненный цикл и ownership channels

Ownership `jobs`:

- вызывающий код отправляет jobs;
- вызывающий код закрывает `jobs`;
- workers получают jobs;
- workers никогда не закрывают `jobs`.

Ownership `results`:

- workers отправляют results;
- вызывающий код получает results;
- pool закрывает `results`;
- вызывающий код и отдельные workers никогда не закрывают `results`.

Pool использует `sync.WaitGroup`, чтобы безопасно закрыть `results`:

```text
Add до запуска workers
Done при завершении каждого worker
Wait в отдельной coordinator goroutine
close(results) после возврата Wait
```

Отдельный worker не может закрыть `results`, потому что не знает, завершили ли отправку остальные workers.

Обычный поток работы:

```text
создать jobs channel
запустить pool
отправить jobs
закрыть jobs
range по results
```

## Когда использовать

- задачи независимы;
- конкурентность нужно ограничить;
- работа поступает потоком;
- нужно контролировать throughput или нагрузку на зависимость;
- результаты можно собирать асинхронно.

## Когда не использовать

- работа мала и строго последовательна;
- задачи сильно зависят друг от друга;
- достаточно одной goroutine;
- semaphore вокруг существующих goroutine яснее выражает ограничение;
- требуются durable queue, retries или распределённая обработка.

## Backpressure

В v1 оба канала небуферизированные. Producer ждёт, пока worker сможет получить job, а workers ждут, пока consumer сможет получить results.

Если никто не читает `results`, workers блокируются при отправке. Они не могут завершиться, `WaitGroup` не может завершить ожидание, а coordinator не может закрыть `results`. Consumer должен вычитать канал полностью, пока следующая версия не добавит cancellation.

## Обработка ошибок

Каждая job может вернуть ошибку в `Result.Err`. V1 сохраняет ошибки отдельных jobs, но не отменяет pool, не повторяет работу и не задаёт глобальную политику обработки ошибок.

## Границы v1

V1 сосредоточена на goroutine, ownership channels, фиксированном числе workers, `sync.WaitGroup` и правильном закрытии канала результатов. Она намеренно не включает `context.Context`, cancellation, deadline, timeout, graceful shutdown, проверки goroutine leak и продвинутую обработку ошибок. Эти темы относятся к Worker Pool v2.

## Тестирование

Тесты проверяют:

- обработку всех отправленных jobs;
- сохранение ошибок jobs в `Result.Err`;
- закрытие `results` после завершения всех workers;
- приведение неположительного числа workers к одному.

Используйте целевые команды для этой лабораторной работы:

```bash
go test ./06-worker-pool-v1/workerpool
go test -race ./06-worker-pool-v1/workerpool
```
